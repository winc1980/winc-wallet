# winc-wallet

サークル内のお金の管理を管理する予定です。

## 概要

WINC Wallet（以下 Wallet）は、サークル規模の組織の会計を複式簿記で管理し、イベントの手続きを止めずに全体の整合性を保つためのサービスです。

WINCは開発のブランド名で、Wallet内では一つの「組織（Organization）」として扱います。特定の組織に依存しない汎用性を持たせます。

## 特徴

- 複式簿記で記録
- イベント単位の会計（夏合宿 など）
- 会計記録・予算計画の連携
- テンプレート機能などを実装し、利用者がやりたいことを素早く行える

## システム

### 三層モデル

- ユーザー：Walletにログインする主体。（パスキー＋メールのOTPで認証）
- 組織（Organization）：会計単位・勘定科目・予算・メンバーが属する先
- メンバー：組織内で精算感情を持つ主体。アカウントを持たない合宿参加者も一応参加できる。

### 組織への参加

参加方法は組織ごとに変えられるのが理想。

暫定では、WINCのGitHubのOrganizationに所属することを条件とする。

### データ分離

組織に属するテーブルにはすべて `org_id` を持たせ、プライマリキーを `(org_id, id)` の複合キーにして、他組織のデータを参照できないようにする。

### 組織ごとの設定

勘定科目と予算区分とそのテンプレート、会計年度の開始月、承認ロール、参加方法。

### ロール・管理者

- 組織の管理者（Admin）
- 組織の会計
- イベントの会計 or 責任者
- 一般

Adminには人気を設ける。

### 組織の作成

権限上は誰でも可。UI上では目立たない位置に配置する。

## インフラ構成

すべてWINCが所有するアカウント上で運用する。

| 役割 | サービス |
| --- | --- |
| アプリケーション | Cloudflare Workers（Workers Paid） |
| データベース | Neon（PostgreSQL） Hyperdrive経由でpgから接続 |
| 証憑・バックアップ | Cloudflare R2（非公開） |
| 定期バックアップ | GitHub Actions |

### 証憑

- 画像はブラウザから直接R2へアップロードする。Workerは権限確認と署名付きURLの発行だけを行う。
- 画像はアップロード前にブラウザで圧縮する。
- オブジェクトキーは組織IDから始める。
- ファイルのハッシュをattachmentsの保存して差し替えを検知できるようにする。

## 技術スタック

１つのWorkerでHonoをエントリポイントにし、APIとReact Routerの画面を載せる構成で始める。

必要になり次第APIと画面を別のWorkerに分け、Service Bindingで繋ぐ。

| 領域 | 採用 |
| --- | --- |
| パッケージ管理・スクリプトランタイム・モノレポ | Bun |
| API | Hono（RPCで型をフロントエンドに提供） |
| フロントエンド | React Router v8 |
| DBアクセス | Drizzle ORM（pg + Hyperdrive） |
| バリデーション・ブランド型 | Effect Schema（Standard Schema経由でHonoの入力検証にも使う） |
| 認証 | Better Auth（アカウント管理のみ） |
| テスト | Vitest |

アプリケーションのコードはWorkersのランタイムで動くため、Bunは開発ツールとして用い、`Bun.file`などのBun固有のAPIはアプリケーションのコードでは使用しない。

### Effectの使い方

HTTP層はHonoのまま、その内側でEffectを使う。

| 層 | 書き方 | 役割 |
| --- | --- | --- |
| Honoのルート | 普通のHono | 認証、入力の検証、Effectの実行、エラーからHTTPレスポンスへの変換 |
| サービス層 | Effect | 承認・請求・締めなどのユースケース、トランザクション |
| ドメイン層 | Effectのデータ型のみ | 仕訳の作成、予算チェックの判定などの純粋な計算 |
| インフラ層 | Effectのサービス実装 | DB、R2、メール送信の具体的な実装 |

#### ドメインのルール

`TaggedError`、Schemaのブランド型、同期的な成功、失敗の型は使って良い。サービスの要求やLayer、入出力は持ち込まず、Effect.tsのResultを型として使用する。
時刻などはサービス層が取得して引数で渡し、サービス層は受け取ったResultをEffectの流れに取り込む。

#### 型付きエラー

会計の失敗（予算超過、締め済みのイベントへの記帳、自己承認、組織に未所属など）をエラー型として定義する。エラー型からHTTPステータスの対応表を一箇所に網羅的に書き、すべてのEffectをそこ経由で実行する。

#### DI

DB・R2・メール送信・現在時刻・ID生成をサービスとして定義し、本番用とテスト用の実装を用意する。
Workersではバインディングがリクエストごとに渡されるため、本番用の実装はリクエストの `c.env` から組み立て、DB接続はリクエストのスコープで確保・解放する。

#### Drizzle

DB呼び出しをEffectで包み、PostgreSQLの規約違反を意味のあるエラー型に変換する。

#### 分割

ルートからはサービス層の関数を１行で呼ぶだけにし、Effectを知らなくても画面とルートを実装できるようにする。

#### Effect 4.0

2026年10月にリリースされたばかりのため、v4の公式ドキュメントを基準にする。
[Effect | Production Grade TypeScript](https://effect.website/)
[Effect 4.0 | Effect Blog](https://effect.website/blog/releases/effect/40)

### 構成のルール

- `loader` / `action` はDBや会計ロジックを直接触らず、 `hc` に `app.fetch` を渡してHonoのAPIを呼ぶ。元のリクエストのCookieヘッダーを転送する。
- 認可とバリデーションの入口はAPIの一箇所にまとめる。
- 会計の正しさはORMに頼らず、マイグレーションのSQLでDB側に保証させる。
- APIのエラーも `c.json` で返し、画面側で型付きで扱えるようにする。

### リポジトリ構成（Bun workspacesによるモノレポ）

```txt

apps/
  worker/   エントリー。Hono に API と React Router を載せる
packages/
  api/      Hono のルート、認可、バリデーション（AppType を公開）
  web/      React Router の画面と loader / action
  domain/   仕訳生成・予算チェック・締め処理などの会計ロジック
  db/       Drizzle のスキーマとマイグレーション

```

#### 依存の方向性

- worker <- api <-(型のみ)- web
- domain <-(DI)- db
- domain <- api

### 認証（Better Auth）

- `packages/api` でHonoの`/api/auth/*`にマウントする。
- Workersでは `nodejs_compat` フラグが必要。
- テーブルはDrizzleアダプターで同じNeonのDBに置く（組織には属さない）
- 初回はメールのOTPで登録し、パスキーを登録する。移行はパスキーでログインし、紛失時はメールで入り直す。
- 組織プラグインとGitHubログインは使わない。
- 組織・ロールは自前で実装し、GitHubによる参加確認のOAuthもBetterAuthとは別に実装する。

### メール送信

Cloudflare Email Service（公開ベータ）を第１候補、Resendを代替とする。
送信処理は関数１つに閉じ込め、後から差し替え可能なサービスとする。

## 会計モデル

仕訳ごとに「勘定科目」と「会計単位」の２軸を持つ複式簿記で記録する。

### 会計単位

一般会計（サークル全体）と、イベントごとの特別会計（例：夏合宿）。

一般会計からイベントへの予算は振替感情（繰出／繰入）で移し、仕訳は会計単位ごとにも貸借を一致させます。

### 精算勘定

メンバーごとの補助科目で、貸し借りと徴収を一つの残高で表す。

プラスはその人がサークルに払うべき額、マイナスはサークルがその人に払うべき額。現地で現金を集めた人もサークルのお金を預かっている人として同じ勘定で扱う。

| 出来事 | 借方 | 貸方 |
| --- | --- | --- |
| 参加費を請求 | 精算勘定（参加者） | 参加費収入 |
| 参加者が振込 | 普通預金 | 精算勘定（参加者） |
| 部員が会場費を立替 | 会場費 | 精算勘定（部員） |
| サークルが立替分を振込 | 精算勘定（部員） | 普通預金 |
| 係が現地で参加費を現金で集金 | 精算勘定（係） | 精算勘定（参加者） |

### 画面での呼び方

個人の精算勘定は「マイウォレット」、イベントの会計単位は「イベントウォレット」。

残高は符号ではなく、「未払い ￥15,000」のように言葉で表す。

### 記録のルール

- 金額は整数の円
- 明細の合計は必ず０（借方を正、貸方を負）
- 確定した仕訳は更新・削除せず、取り消し仕訳で訂正する
- 利用者は簿記を意識しない。操作テンプレートを選ぶと裏で自動で仕訳が作られる（テンプレートの内容は別途検討）

## 徴収管理

イベントごとに参加者リストを持ち、請求を「予定」として管理し、確定時に仕訳を起こす。

- 参加者ごとの請求額（学年別料金や飲酒の可否などに対応）
- 支払済みかどうかの確認（精算勘定の残高で確認）
- キャンセル時の返金は、請求の取り消しとして扱う

## 予算・計画

予算は仕訳帳の外に持ち、仕訳帳は起きた事実だけを記録する。予算は勘定科目よりも一段粗い予算区分（会場費、食費、交通費、備品など）で立てます。

### 年度予算

一般会計の計画。会費などの収入、備品などの支出、各イベントへの繰出額を持つ。

### イベント予算

収入は「一般会計からの繰入＋参加費」。予算行を固定費と１人あたりの費用に分け、想定人数から必要な参加費を計算できるようにする。

### 予算対実績

予算区分ごとに、予算・実績（確定仕訳）・見込み（実績＋未入金の請求＋承認済み未払い）を並べて表示

### 補正予算

予算は上書きせず版として履歴を残す。

## 承認ルール

現場の運用の速度を優先し、イベント内の支出は見込みがイベントの予算総額を超えない限り、イベント会計担当の承認だけで確定する。

- 予算区分ごとの超過は警告のみ。予算総額を超える場合は、全体会計が補正予算を承認する。
- イベント担当が承認した取引は全体会計に通知され、全体会計が確認済みをつける。
- 同時承認による予算超過を防ぐため、承認処理では会計単位をロックする。

### イベントの締め

イベント内の全メンバーの精算残高がゼロになったら締められる。
回収できない参加費などは一般会計へ振り替えてから締め、締めた後の記録はロックする。
